# ТЗ: система автоматизации и продаж селфботов «Luna Fleet»

## 1. Общие положения

**Продукт:** подписка на селфбота «Луна» (ответы по триггеру, треды, цитаты чужих сообщений,
веб-поиск на каждый запрос, «рассуди» с занятием стороны, «перескажи» — выжимка чата,
«экспорт» — выгрузка истории в файл, «переведи» — перевод сообщений,
характер на выбор из пресетов).
Клиент предоставляет свой номер Telegram + API ID/Hash с my.telegram.org.
Железо, AI-провайдер — наши, включены в тариф.

**Модель размещения:** парк дешёвых VPS, **2–3 бота на сервер** (слоты `a`, `b`, опционально `c`).
У каждого VPS свой IP — он и есть изоляция (прокси не используются).
Освободился слот → заселить нового клиента. Сервер пуст → удалить сервер (стоп почасовой оплаты).
Оркестрация — через API VPS-провайдера.

**Управление — только Telegram-бот** (Bot API, aiogram): витрина, продажа, онбординг,
личный кабинет (настройки бота), админка парка. Веб-панели нет.

**Оплата:** AnyPay — основной провайдер (карты, СБП). Платёжный слой модульный:
интерфейс `create_invoice()/check_webhook()`, вторым встанет любой агрегатор
(CryptoBot и др.) без переписывания ядра.

**Конфигурация ботов — JSON, не env.** Каждый бот читает один `config.json`
(имя, триггер, характер, фильтры, лимиты, ключи). Файл генерирует и правит
автоматика (Fleet Bot), руками не трогается. Единственная env-переменная —
`CONFIG_FILE` (путь к конфигу).

**Имена команд — в коде, не в конфиге.** Команда «рассуди» и все будущие команды —
константы (`COMMANDS` в `luna_bot.py`), к триггеру приклеиваются автоматически:
`«<триггер> <команда>»` (например, «луна рассуди»). Переименование бота клиентом
не ломает команды.

## 2. Требования к VPS-провайдеру (критерий выбора)

Обязательное HTTP API: создать сервер из снапшота/образа с cloud-init,
получить IP/статус, удалить сервер, биллинг/баланс.
Тариф: 1 vCPU / 1–2 ГБ RAM / 10–20 ГБ SSD, **почасовая оплата**,
переустановка из снапшота за минуты. SSH по ключам.
Дата-центровый IP считается расходником. Кандидаты на сравнение:
Aeza, Timeweb Cloud, PQ Hosting, Hetzner. Выбор фиксируется до этапа 4.

Расчёт: 1 бот ≈ 60–120 МБ RAM idle → 3 бота + система ≈ 0.5–1 ГБ.
Тарифа 1–2 ГБ хватает с запасом.

## 3. Архитектура системы

```
                    ┌─────────────┐
                    │  Fleet Bot  │  Telegram Bot API (aiogram)
                    │ (продажи +  │── AnyPay API (счета, вебхуки)
                    │  управление)│── Provider API (создать/удалить VPS)
                    └──────┬──────┘── SSH (деплой, конфиг, логи)
                           │        ── AI-шлюз (LiteLLM: бюджеты, биллинг)
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ VPS #1   │ │ VPS #2   │ │ VPS #N   │
        │ luna-a   │ │ luna-a   │ │  ...     │
        │ luna-b   │ │ luna-b   │ │          │
        │ (luna-c) │ │ (luna-c) │ │          │
        └──────────┘ └──────────┘ └──────────┘
        2–3 docker-контейнера luna:vX.Y, конфиги clients/<id>/config.json
```

**Компоненты:**
1. **Fleet Bot** — единственный управляющий узел. Модули: витрина/тарифы, онбординг,
   оплата, личный кабинет, админка парка, планировщик (биллинг, рестарты, сверка).
2. **Registry (БД)** — SQLite/PostgreSQL: `clients`, `bots` (client→vps, slot a/b/c, статус),
   `servers` (provider_id, ip, used_slots, статус, цена/час), `payments`, `ai_usage`.
   Единственный источник правды; все операции транзакционны.
3. **Образ Luna `vX.Y`** — один на всех, версионируется, пушится в container registry.
   На VPS только `pull`, сборки на месте нет.
4. **Снапшот VPS** — Docker + compose-шаблон (`docker-compose.fleet.yml`) + deploy SSH-ключ.
   Новый сервер поднимается за минуты.
5. **AI-шлюз (LiteLLM)** — один, рядом с Fleet Bot: один апстрим-ключ,
   виртуальный ключ на клиента, дневной лимит, учёт расхода (себестоимость).

## 4. Функциональные требования

### 4.1. Витрина и продажа
- `/start` → тарифы (срок 30 дней), выбор характера из пресетов (карточки),
  кнопка «Оплатить» → счёт AnyPay → вебхук → подписка активна.
- Онбординг-мастер после оплаты: ① API ID/Hash (инструкция my.telegram.org) →
  ② номер телефона → Fleet Bot инициирует логин на свободном слоте →
  ③ клиент вводит код из Telegram в чат Fleet Bot → сессия создана →
  ④ имя бота/триггер → бот запущен, сообщение «всё готово».
- Триал: флаг `trial` в registry, урезанный `daily` лимит (на усмотрение, заложить).

### 4.2. Личный кабинет клиента
- Настройки бота: имя/триггер, характер (смена пресета), белый/**или** чёрный список чатов
  (взаимоисключающие), игнор каналов/групп, лимиты. Применение = Fleet Bot правит
  `config.json` клиента по SSH и рестартит его контейнер (секунды).
- Статус: онлайн/офлайн, подписка до, кнопка «продлить», статистика ответов за неделю.
- «Бот молчит» → автодиагностика (пинг VPS → статус контейнера → хвост логов →
  валидность сессии) → автофикс (рестарт) или тикет админу с логом.

### 4.3. Управление парком
- **Заселение:** оплата → свободный слот (предпочтение — самый заполненный сервер) →
  нет места → создать VPS из снапшота → дождаться IP → SSH-деплой
  (pull образа, генерация `config.json` + уникальных задержек + device-фингерпринта,
  старт) → запись в registry.
- **Выселение:** конец подписки + grace 3 дня → стоп контейнера, архив volume
  (сессия+БД, хранить 30 дней) → слот свободен. Сервер с `used=0` → удалить через API.
- **Планировщик:** ежедневно — подписки/оплаты/напоминания; еженедельно — rolling restart
  ботов по одному слоту (память Telethon); ежечасно — health-сверка
  (контейнер жив? сессия валидна?).
- **Анти-аффинити:** два бота одного клиента — никогда на один VPS.

### 4.4. Админка (тот же Fleet Bot, whitelist Telegram ID)
- Парк: серверы, слоты, аптайм, расход AI на клиента, выручка/расходы.
- Операции: переселить бота, пересоздать VPS, стоп/архив клиента, рассылка.
- Обновления образа: `выпустить vX.Y` → rolling update (pull + recreate по одному,
  с проверкой health). Данные клиентов в volume не трогаются.

### 4.5. Оплата и биллинг
- AnyPay: счёт, вебхук с проверкой подписи, продление; возвраты — вручную.
- Себестоимость на клиента (VPS/слоты + AI-расход) видна в админке для контроля маржи.

## 5. Нефункциональные требования
- **Безопасность:** секреты только в `config.json`/volume, никогда в код и логи;
  SSH только по ключам (отдельный deploy-ключ); сессии и архивы шифруются;
  ключи AnyPay/провайдера — в env управляющего хоста; админка по whitelist ID.
- **Надёжность:** мутации парка через registry-транзакции; идемпотентность
  (повторный вебхук ≠ 2 подписки); архив ушедшего клиента 30 дней.
- **Наблюдаемость:** хвост логов по кнопке из админки (SSH `docker logs --tail`),
  позже — Loki; алерты: бот down >10 мин, VPS недоступен, AI-бюджет 80%.
- **Масштабируемость:** Fleet Bot не знает числа серверов — всё через планировщик;
  ноль ручных операций на клиента в штатном сценарии.

## 6. Этапы разработки
1. **Luna под флот:** JSON-конфиг, команды в коде, device-фингерпринт,
   fleet compose-шаблон (2–3 слота, mem-лимиты, ротация логов), версионированный образ.
2. **AI-шлюз + схема registry.**
3. **Ручной провижининг скриптом** + снапшот VPS. Прогон 2–3 тестовых ботов неделю,
   замер RAM/стабильности.
4. **Fleet Bot: продажи + онбординг + AnyPay.** Первые платящие.
5. **Автоматика парка:** заселение/выселение/удаление пустых VPS, планировщик,
   автодиагностика.
6. **Админка, себестоимость, rolling updates.**

## 7. Открытые вопросы (зафиксировать до этапа 4)
- Триал: да/нет, длительность, лимиты.
- Бан аккаунта клиента: дисклеймер + платное восстановление сессии.
- 3-й слот на VPS включать сразу или держать `a/b` + резерв (рекомендация: резерв
  под переселения без даунтайма).
